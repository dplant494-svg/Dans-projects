## 2. Precharge email — the PDF, and only the PDF

Dan's standard: the attachment the rig receives must be **the generated PDF, exactly**.

the PDF bytes in the post and the flow attaches them. Handoff:
`PRECHARGE-HANDOFF-SHEETPDF.md`. Flow change once it lands: attachment 1 removed,
attachment 2 becomes the PDF (two clicks, instructions in the handoff). No scanner
change.

## 4. Scanner cache — v2.45

"Recheck and post only if modified", exactly. The scanner keeps a small state file of
what it extracted from each file, keyed on name, size and last-modified time; an
unchanged file is not re-read. The aggregate is still rebuilt every run from the
cached pieces, so every dedup and newest-wins rule works as today. Digests and report
copies already work this way. A handoff back to the reporting-tools session is not
needed for this one: it changes nothing they post.

## 5. Daily Checks off the Report List

**What this changes.** The database can be built and proven now, on the trial, by us,
with no IT resource: the engine is Azure SQL under Fabric, so the recommendation
already agreed with the reporting-tools session stands. The January ask to IT becomes
**"attach a paid Fabric capacity to the WCE workspace before the trial ends"**, which is
a licence line, not an infrastructure project. The trial deadline is the date to prove
the schema, the loader and parity by.

**One open technical question, ours:** how the scanner authenticates to the Fabric
database from a scheduled task with no installs. Fabric SQL uses Entra sign-in, not a
SQL password. The clean route is an app registration (service principal) whose token
the scanner fetches with a plain web call and hands to `SqlConnection`; the app
registration is a small Entra admin ask and belongs on the same ticket as the service
identity IT already want for notifications. To be answered in the timeline reply.

**Not for production on the trial.** Anything built there must move to a paid
capacity or be re-created; the pack says so plainly.

database can still start now, and the engine recommendation in the timeline reply

a flow or the Web API, not a SQL connection). With neither, January, as planned.

**On "we would not need all these HTMLs":** the dashboards stay, by Dan's decision
(same pages, ISIT maintain them). What a database replaces is the *digests*: Copilot
Studio can read Dataverse tables directly, and Azure SQL through a connector, so once
the data is in a database the agent is pointed at that and the Digests library is
retired. The digests are the bridge that gets Copilot live this week rather than in
February.
