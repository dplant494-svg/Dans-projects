## 1. Embedding — about ten lines on your side

```html
<body>
  <script src="gate-config.js"></script>       <!-- 1. BEFORE the gate -->
  <!-- 2. paste gate-fragment.html here (style + div + script) -->

  ... existing calculator markup ...

  <!-- 3. a tab/panel of your choosing -->
  <button type="button" onclick="showTab('inbox')">Requests inbox</button>
  <div id="tab-inbox"><div id="pcinbox"></div></div>

  <!-- 4. paste inbox-fragment.html here (style + script) -->
  <script>
    // 5. mount once; onOpen = your existing ?req= loader, called directly
    PrechargeInbox.mount(document.getElementById('pcinbox'), {
      onOpen: function (id) { loadRequestById(id); showTab('calculator'); }   // your function names
    });
  </script>
</body>
```

Notes:

- **`onOpen` is the only wiring.** Point it at whatever your Rev 72 `?req=`
  loader calls internally, so a row click fills the calculator **without a page
  reload**. If you omit `onOpen`, the fragment falls back to navigating to
  `?req=<id>`, which your loader already handles — it works with zero wiring,
  just slower.
- `indexUrl` defaults to `requests/index.json`, relative to the calculator —
  same folder assumption as your loader. Override in `opts` if you must.
- `refreshMs` defaults to 60000. The fragment returns `{ refresh, destroy }`.
- The gate fires a `pcgate-unlocked` event on `document` if you want to defer
  anything until after login. Mounting the inbox before unlock is harmless
  (it only fetches the index).
- The fragment writes **only** `localStorage['pc-opened']` (its own "opened"
  note). It never touches `requests/` — the scanner stays the one writer.
- Keep `#pcgate` and `#pcinbox` ids unique in the page; the CSS is scoped to
  them and nothing else.

## 2. What the gate is — say this plainly in your own docs too

It is a **curtain, not a lock.** It hashes the typed password (SHA-256 with a
fixed salt) against `gate-config.js` and hides the page until it matches;
the login is kept in `localStorage` for 12 hours, or indefinitely with
"remember on this computer". It stops people using the pages. It does **not**
stop someone who already knows a direct URL to `requests/<id>.json` on the
open sandbox share. Dan has accepted that for the sandbox. Before production,
the folder needs server-side authentication or encrypted payloads — the
scanner side can add AES encryption of the request files with the same
password when that day comes (your loader would then decrypt; a small
change, and it is why the gate already uses a proper hash rather than the
plain password).
