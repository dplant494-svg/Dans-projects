## 4. Scanner cache — v2.45, built 14 September

"Recheck and post only if modified", exactly, and built the simpler of the two ways.
The plan above said a per-file cache. Reading the loop again: one file feeds fifteen
different aggregates (reports, precharge inbox, planning, day log, rig checks, CBM
grades, TOPSET, compliance, digests, report copies...), so a per-file cache means
recording every one of those per file and replaying them, which is a rewrite of the
900-line loop with no real data here to prove it against. Principle 4 of the
Precharge Pro session's document applies: a cache that quietly measures less than the
full scan is worse than no cache.

So v2.45 does the honest version. Every output of the scan is a pure function of the
input files, `config.json`, the script version and today's date. The scanner hashes
exactly those (every scanned file's name, size and last-modified time, the config
text, the version, the date) and records the hash in `scan-state.json` next to
`config.json`, **only after a run that found reports and completed every deploy
step**. The next run computes the same hash first: if it matches, nothing can have
changed, so it refreshes the "Data updated" stamp in the three data files and their
deployed copies and stops. One changed byte in any file, a new file, a removed file,
an edited config, a new day, a failed deploy last time, a missing deployed file, or
`-Force`: full scan, identical to v2.44.

Measured here on the 16-file test set: full scan 9.1 s, unchanged run 0.8 s. On
Dan's 270 files the unchanged run is the same 1 s; it never opens a report. The
10-minute task therefore does real work only in the ten minutes after a post, and at
most once a day otherwise (the date is in the hash because TOPSET overdue flags
compare due dates with today).

Also in v2.45: digests say **"Critical items (0): None recorded"** and **"Actions
raised during the visit (0): None recorded... anything that reads like a task in the
text below was not raised as an action"** when a report raised nothing. Copilot was
improvising actions from narrative; now the digest tells it there were none. First
v2.45 run rewrites every digest once (266 small files sync, Copilot re-indexes in
minutes).

## 25. Photographs and attachments out of the JSON (added 21 September, reworded after Dan)

**For the rig, nothing changes: one Post button.** The split is inside the tool and invisible

at the pictures as pictures.

## 26. A photo review agent for CBM (added 21 September, Dan's ask)

Dan's question: can an AI agent live in the photographs and recognise things, for example a
grade change between CBM inspections, or a type of damage or a failure? Yes, and it is the
strongest reason for item 25: it needs photographs as files with stable keys (rig, equipment,
item, inspection date), which the CBM payload already gives (`cbm_<equip>_<item>_ph`).

What it would do, per new CBM report, with no change to the crew's work:

- For every photographed item, find the previous inspection's photograph of the same item on
  the same rig, put the two side by side with the grade given then and now, and say what it
  sees: corrosion, cracking, wear, scoring, deformation, missing or loose parts, and whether
  the condition looks worse, the same or better than last time.
- Flag three things for the WCE Superintendent: a grade that looks inconsistent with the
  photograph (a G1 with visible corrosion), a grade that worsened since the last inspection,
  and a damage type that the report text does not mention.
- Write a review sheet per report (item, both photographs, both grades, the agent's view and
  its confidence) into the report's folder, and put a line on the dashboard's CBM row: "3
  items flagged for review". **It never changes a grade.** Grades stay the inspector's; the
  agent is a second pair of eyes, in keeping with the evidence rule.

SSORT (tools handoff §10, in progress: an agent grading against corrupted criteria would look
authoritative and be wrong); the CBM grade photo reference set the tools session is building

IT's answer on which vision model may see rig photographs. Two routes: Azure OpenAI with a
vision model inside Seadrill's own tenant (the IT-friendly one, no data leaves), or the Claude
API (needs an approval for data leaving the tenant). Either runs as a scheduled job beside the
scanner on the server, reading the new files and writing the review sheets.
