## 4. Scanner cache — v2.45, built 14 September

"Recheck and post only if modified", exactly, and built the simpler of the two ways.
The plan above said a per-file cache. Reading the loop again: one file feeds fifteen
different aggregates (reports, precharge inbox, planning, day log, rig checks, CBM
grades, TOPSET, compliance, digests, report copies...), so a per-file cache means
recording every one of those per file and replaying them, which is a rewrite of the
900-line loop with no real data here to prove it against. Principle 4 of the
Precharge Pro session's document applies: a cache that quietly measures less than the
full scan is worse than no cache.

So v2.45 does the honest version. Every output of the scan is a pure function of the
input files, `config.json`, the script version and today's date. The scanner hashes
exactly those (every scanned file's name, size and last-modified time, the config
text, the version, the date) and records the hash in `scan-state.json` next to
`config.json`, **only after a run that found reports and completed every deploy
step**. The next run computes the same hash first: if it matches, nothing can have
changed, so it refreshes the "Data updated" stamp in the three data files and their
deployed copies and stops. One changed byte in any file, a new file, a removed file,
an edited config, a new day, a failed deploy last time, a missing deployed file, or
`-Force`: full scan, identical to v2.44.

Measured here on the 16-file test set: full scan 9.1 s, unchanged run 0.8 s. On
Dan's 270 files the unchanged run is the same 1 s; it never opens a report. The
10-minute task therefore does real work only in the ten minutes after a post, and at
most once a day otherwise (the date is in the hash because TOPSET overdue flags
compare due dates with today).

Also in v2.45: digests say **"Critical items (0): None recorded"** and **"Actions
raised during the visit (0): None recorded... anything that reads like a task in the
text below was not raised as an action"** when a report raised nothing. Copilot was
improvising actions from narrative; now the digest tells it there were none. First
v2.45 run rewrites every digest once (266 small files sync, Copilot re-indexes in
minutes).

## 30. Automatic CBM photo grading — a model that suggests the 1 to 5 grade from the photograph (added 24 September, Dan's brainwave)

**Dan's ask:** a second agent, after the Copilot one, that looks at every CBM photograph and
grades it 1 to 5 from the condition it sees; thousands of graded sample photographs will
accumulate over time. **Answer: yes, possible, and worth planning for, with three honest
limits.** It extends item 26 (the review agent): 26 compares and flags, 30 proposes a grade.

**Why it is possible here in particular.** Every posted CBM report already pairs each
photograph with the crew's grade, the crew's note and, from SSORT 148, NOV's task wording
(`_ph` + `_gr` + `_cm` + `cbmlabels`), keyed by rig, equipment class and task id. That is a
labelled training set that grows by itself, at no cost to anyone, every inspection. Nobody
has to grade photographs for the model; the fleet is doing it already, against NOV's own
scale, which is exactly the label we want.

**The three limits, stated up front so the plan is honest:**

1. **A grade is a judgement on the task, not always on the picture.** Some tasks are graded
   from a measurement (a groove depth, a bore diameter), a function or a document; the
   photograph shows the item, not the number. The model can only learn the tasks where the
   photograph carries the evidence (visual inspection of surfaces, seals, blades, corrosion,
   scoring, wear). The dataset will show which tasks those are: where the model agrees with
   the crew, the picture carries the grade; where it never does, it does not.
2. **The labels are noisy.** Entry 21's Grade 3 confusion, the corrupted criteria before
   SSORT 148, one crew's G2 being another's G3. A model trained on that inherits it. The fix
   is time and volume: only data graded from SSORT 148 onwards (criteria on screen, wording
   on the key) goes into the training set, and the model is judged per equipment class, not
   as one number.
3. **It never grades.** The crew grades; NOV's criteria are the measuring stick; the auditor
   reads the crew's grade. The model writes a **suggested grade with a confidence** next to
   it, and the dashboard shows the disagreements. Same rule the tools session applied to
   conditional triggers and we applied back (rolling handoff 27): a computed judgement is
   never posted or displayed as a recorded fact. This also keeps it out of the MOC and
   HAZID scope of a process change; it is a review aid.

**Not Copilot Studio.** The Copilot agent answers questions over the report digests; it
cannot run a vision model across thousands of photographs on a schedule. This is a
different kind of thing: a vision classifier, trained on our own photographs, run as a job
beside the scanner. Two candidate routes, the same two as item 26: Azure AI Vision custom
image classification or an Azure OpenAI vision model inside Seadrill's tenant (nothing
leaves; IT's preferred shape), or a Claude vision model with the NOV scale and worked
examples per grade in the prompt (faster to try, needs the data-leaving approval).

**Build order, so the cheap part starts now and the expensive part waits for the data:**
