## 7. The database — added 11 September 2026

Dan's question was direct: *"a further evolution of this is a database… can you help
us build this? if not can you tell us what type of database we need… this will be to
start in january if you cannot assist as we will need an IT resource. I would like to
get started before then."*

### 7.1 The answer: most of it needs no IT resource, and can start now

The database splits cleanly, and the larger half needs nobody outside Technical
Services because **none of it requires an instance to exist.** A schema, a loader and
a query layer are written and tested against files — and we have the files.

| Built here, from September | Needs IT / ISIT, from January |
|---|---|
| the schema and the DDL | the instance, networking, firewall |
| the loader that reads today's `.json` and populates it | identity, SSO, role grants |
| the parser for the existing reading-key convention | secret and credential management |
| the operational rules as views | backup, DR, monitoring, patching |
| idempotency and de-duplication, so a re-post is safe | security review and penetration test |
| a proof run over every posted report, with a data-quality report | one review pass over the DDL by whoever owns the platform |
| the read queries you need | the cutover itself |

So page 1 now starts the database in **September**, not January, and the row
**"Database instance provisioned — FIRST IT RESOURCE NEEDED"** is the January ask.
Three bars carry a yellow outline meaning *buildable now, no IT resource*.

**One honest limit:** the DDL cannot be executed against the real server from here, so
it needs one review pass by whoever owns the platform before it is trusted.

### 7.2 What kind of database

**Three stores, not one:**

1. **Relational core** — `rigs`, `reports`, `readings`, `actions`, `photos`. The part
   you query, trend and join.
2. **The raw payload as a JSON column on `reports`**, stored verbatim and never
   edited. Lossless, and a new report type needs no migration.
3. **Photographs in object storage** (Azure Blob). The database holds the pointer,
   the SHA-256 and the byte count — never the image.

**Engine:** **Azure SQL Database** if Seadrill IT are Microsoft-aligned, which they
are — SharePoint and Power Automate already, and it has native JSON via `OPENJSON` /
`JSON_VALUE`. **PostgreSQL** is the better technical fit (JSONB with GIN indexing
suits this document shape better) and is the recommendation if we get a free choice —
but an unsupported database is a worse outcome than a supported one that is slightly
less elegant. **Not** a document store, because the data needs joins and time-series
trending. **Not** a time-series engine, because 1.1 M rows a year does not warrant it.

**This is now a parked question on page 1:** which of the two ISIT will actually
support, and who will own the instance.

### 7.3 Two things in here that are yours

- **`readings` is long and narrow, one row per reading.** The tools already emit a
  flat key — `dc_hpu__hydraulic_pressure` with `_cmt` / `_unit` / `_psi` companions —
  so there is no transformation to do. The loader only splits the key into section
  and item. **If your scanner already derives anything from those keys, tell me, so
  the loader and the scanner agree rather than diverge.**
- **`needs_attention = (status = 'fail' OR comment <> '')` lives in the database**, as
  a view, not in each consumer. You currently apply that rule yourself. Once it is in
  the database there should be exactly one definition of it — **please confirm the
  rule as you implement it today matches, so we do not end up with two.**

### 7.4 How the migration runs — page 4

**A** load the history read-only (files untouched) → **B** dual-run, scanner writes
files *and* database, both live → **C** prove parity report by report and reading by
reading → **D** point the dashboards at the database, file pipeline retained as
fallback.

**Parity is the gate, not a date.** Steps B and C are mostly your work, which is why
§4.1 asks you to size them.

### 7.5 Grounding

The schema is shaped from a profile of the real posted files, not from a guess: 27
reports, 37.9 MB, 151 embedded images, nesting depth 7, 12 distinct top-level keys, 7
discipline-specific sub-objects on a single tile, 67 keyed readings in one daily-check
round, and a largest report of 14.3 MB that is **100% photographs**. Repeatable — the
profiling script is in the folder.

### 8.3 New item — the SSCE allocation one-way door

`SSCE-ALLOCATION-RELEASE-HANDOFF.md` is a **request addressed to you**, not an answer,

SSCE is a **loan pool**, not a transfer, so displayed availability can only ever

**One technical flag, from our own scar tissue.** The proposed identity rule is
*asset + oem + serial, or requestId if carried*. That is the same shape as the
de-duplication key on page 3, and it carries the same trap: **a missing or blank serial

look different.** Whichever store this ends up in, that key needs a sentinel for the
absent case. It is design decision 4 on page 4, and it has already bitten this
programme once.
