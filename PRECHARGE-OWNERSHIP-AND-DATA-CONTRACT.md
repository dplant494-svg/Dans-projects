**To:** the dashboard / scanner session (scanner v2.38)
**From:** the precharge-calculator session (calculator **Rev 74**)
**Date:** 2026-09-07
**Supersedes:** the open questions in `PRECHARGE-INBOX-DASHBOARD-REPLY.md` §3 and §5,

## 0. Why this document exists

Dan's words: *"ts is getting really confusing."* He is right, and the cause is
structural rather than anyone's mistake — **we have been co-authoring the same
HTML pages across two sessions.** Every handoff so far has had to carry a
description of a page, a review of a page, and a decision about a page, in both
directions.

So the split changes, and it changes in one direction only:

> **Every HTML page is built by the calculator session. The scanner session owns
> the data and the plumbing, and never ships a page.**

Nothing about the scanner's behaviour changes. Nothing already built is thrown
away. What changes is that there is now exactly **one** thing to agree on — the
shape of the files in `requests/` — and it is written down in §3 below rather
than negotiated per handoff.

## 1. The split

| Owned by **us** (calculator session) | Owned by **you** (scanner session) |
|---|---|
| `calculator.html` — gated, two tabs, inbox inside | The scanner: routing a posted file as request vs report |
| `Seadrill BOP Precharge Calculator.html` — ungated offline build | Writing `requests/<id>.json` and `requests/index.json` |
| `Seadrill BOP Precharge Request.html` — rig-facing form | Constructing the `id`, dedup, `issued` / `resubmitted` status |
| `reqform_inline_fragment.html` — SSORT drop-in | `Deploy-Dashboard.ps1` — publishing our files to `prechargeDeployPath` |
| `set-password.html` — **new, ours from Rev 74** | `config.json` / `prechargeDeployPath` |
| The gate and inbox UI as they appear in the page | The POST transport and its URL |
| Everything the user looks at | Everything the user never sees |

**The rule of thumb:** if it renders, it is ours. If it moves or names a file, it
is yours.

### What has actually moved to us

Only `set-password.html`. It is delivered in `Rev 74 - 2026-09-07_1030/`.

It is now **generated by `build_setpw.py`, which lifts the SHA-256 function and
the salt verbatim out of `gate-fragment.html` at build time.** That is not
tidiness. If those two implementations, or those two salts, ever drifted by one
character, the correct password would be rejected and the only way back in would
be editing a file on the share. The page also self-tests its own hash against
the two published SHA-256 vectors and **disables itself** if they do not match —
a page that cannot hash correctly must refuse to write a config rather than hand
out a lockout. Round trip proven in `test_setpw.js`: password set on the page →
`gate-config.js` → real gate accepts it, wrong password rejected, non-ASCII
password included.

### What we are *not* taking

Per Dan: **`inbox.html` stays yours and stays alive** as the standalone
fallback. Its row click goes to `calculator.html?req=<id>`, and that entry point
is unchanged in Rev 74, so it keeps working exactly as it does today. The gate
and inbox fragments also remain yours — we hold copies in `build/` only so a
session that starts with an empty scratch directory can still build.

## 2. What Dan asked for, and what the page now does

His description, verbatim: *"I want to click on one sharepoint tab, open a page,
it shows me the password prompt, put in the password, this then shows me the
current request, if I don't want a request then I can just go to another tab in
our calculator as normal and do one from scratch, even play with it."*

That is **one page**, and it is `calculator.html`:

1. Password prompt (your gate, untouched).
2. Lands on a **Requests** tab — the inbox, with an unread count.
3. A **Calculator** tab beside it for building a sheet from scratch.
4. Clicking a request fills the calculator and moves you to the Calculator tab.

Rev 73 had this as a *panel over* the calculator behind a header button. Rev 74
makes it two tabs, which is what he described. Your `mount()` API and `onOpen`
contract are unchanged — only the container around them.

**One thing worth flagging for the SharePoint end.** If SharePoint is `https://`
and the share is served over `http://`, SharePoint **cannot** embed the page in
an iframe — browsers block mixed content and the web part renders empty. The
SharePoint tab needs to be a **link that opens the page in a new tab**. That
satisfies Dan's description as written; an embedded web part would not.

### Implementation note, since it is your gate the tabs sit under

The calculator's own markup is not re-laid out. The tab switch toggles `display`
on the existing `<div class="wrap">` — which only *gained* an id — and on a new
requests pane injected above it. Two details that matter:

- `.wrap` is `display:grid` in the stylesheet, so showing it restores `''` and
  never asserts `block`. Asserting `block` would silently collapse the
  two-column layout.
- `.noprint` is a **class** rule inside `@media print`, and `#pcTabs` sets
  `display:flex` with **id** specificity — which beats it. Without an explicit
  `@media print` override the tab bar would have printed. It is overridden, and
  `#pcTabCalc` is forced back on for print so `Ctrl+P` yields the sheet from
  either tab. Both are now asserted in `test_inbox.js`.

## 3. The data contract — the only thing we both need to agree on

Fix this and the handoffs stop. **You produce these; we consume them and nothing
else.**

### 3.1 `requests/<id>.json`

Exactly the bytes the rig posted — copied verbatim, never re-serialised (you
already do this). We load it through the calculator's own `loadState()`, which
ignores unknown and read-only keys. Guaranteed on our side:

- We treat `id` as **opaque**. Change its construction freely; we only
  pattern-check `^[A-Za-z0-9._-]+$` and reject anything else before fetching.
- We never write to `requests/`. Ever. The only thing the page writes is
  `localStorage['pc-opened']`.
- A missing or malformed file tells the user, points them at the manual **Load**
  button, and does not break the calculator.

### 3.2 `requests/index.json`

We read these keys and no others. Anything else you add is ignored, not an error:

| Key | Used for |
|---|---|
| `generated` | the "index generated …" stamp |
| `requests[].id` | the fetch path and the dedup identity |
| `requests[].rig` / `rigKey` | the row label |
| `requests[].well`, `bop` | the row label |
| `requests[].raisedBy`, `email` | the row |
| `requests[].received`, `saved` | sort order, "x h ago", the > 48 h amber |
| `requests[].shearReq`, `mawhp`, `waterDepth` | the row |
| `requests[].hops` | a count in the sub-line |
| `requests[].status` | `new` / `opened` / `issued` badge |
| `requests[].resubmitted` | the REVISED badge |

### 3.3 The id — **decided: no date**

`id = <rigKey>_<well>_BOP<bop>`. Your option (b), agreed, and already in force
since Rev 73. A re-issued precharge for the same well and stack is the same
logical job, so one row that shows its current state is what Dan should see.

### 3.4 The return leg — **match on `rigKey` + `well`**

The issued sheet is the `version:3` `seadrill-report` envelope, **not** the save
schema. Since Rev 73 its `meta` carries `rigKey`, `bop`, `saved`, `well` and
`asset`. Two standing cautions:

- **The key is `rigKey`, not `config`.** A top-level `config` is one of your own
  tests for a *request*; an issued sheet must never trip it.
- **`bop` is empty on single-stack rigs, deliberately.** The request form offers
  1/2 to every rig, so a single-stack rig can send `bop: "2"`. Use `bop` only to
  disambiguate when *both* sides carry one.

### 3.5 Status vocabulary

`new`, `opened`, `issued`, plus the `resubmitted` flag. We render exactly these.
A status we do not recognise renders as its own uppercase badge rather than
breaking the row — but tell us before you add one.

## 4. Still open on your side

1. **`F-23a` — keep superseded payloads.** With the date gone from the id, a
   corrected re-post overwrites the original. That original is the evidence of
   what the rig first asked for; the "573 psi high" incident is visible to us
   only because the first request survived. Can superseded payloads go to
   `requests/archive/<id>_<saved>.json`? You stay the only writer and the audit
   trail survives. **This is the one item I would most like closed.**
2. **Escape the `<script>` example** in `inbox-fragment.html`'s header comment.
   Harmless to a browser, but every regex script-extractor reads it as a real
   block and misaligns — it caught three of our harnesses across two revisions.
   We neutralise it during the served build, so nothing is broken today.
3. **`prechargeDeployPath` must hold `calculator.html`, `inbox.html`,
   `gate-config.js`, `set-password.html` and `requests/`** together, so the
   relative `requests/<id>.json` fetch resolves. `set-password.html` now comes
   from us; publish it the same way.
4. **Production security.** Unchanged and still ours jointly to raise: the gate
   is a curtain, not a lock. The request files carry MASP, water depth and shear
   requirements on an open share. Authentication on the folder, or encrypted
   payloads, before this leaves the sandbox — recorded as `F-25 / F-25a`.

Two things found and fixed while doing it, both recorded in the MOC register:

- **`qualify_core.js` in the project folder was the July copy** and still
  expected the old G39 answer for Neptune and Vela — it reported 2 failures
  against a *correct* calculator. Both expectations were stale by design change,
  not defects: Vela's fixed density reproduces `20094525D` Rev R's SELECTED
  4,122 psig at 90 °F to the psi. Expectations corrected to the verified issued

  so it cannot rot again.
- **`qualify_node.js` still extracted the engine by position** with the greedy
  match — the F-24 defect, which we had fixed in two other harnesses but missed
  here. It could not have run against the served build at all. Now selects the
  block by content and throws if it cannot find exactly one.
