## 2. Who writes what — the only rules that matter

| File / folder on the share | Written by | Never touched by |
|---|---|---|
| `precharge\calculator.html`, `set-password.html` | `Deploy-Dashboard.ps1`, copying **your** files from `D:\TSC-Dashboard\precharge\` unchanged | the scanner, the calculator page |
| `precharge\gate-config.js` | `Deploy-Dashboard.ps1`, copying Dan's generated file | you, the scanner, the page (it only reads it) |
| `precharge\gate-fragment.html` | `Deploy-Dashboard.ps1` from our repo copy | you (F-41: we send it, you inline it) |
| `precharge\requests\**` | `Update-Dashboard.ps1` only, on its 10-minute schedule | everyone else. The page reads; `localStorage['pc-opened']` is the only thing it writes, in the browser |
| `precharge\index.html`, `inbox.html`, `inbox-fragment.html` | nobody — retired; the deploy script deletes them if found | — |

Two consequences:

- **A file you place directly on the share will be overwritten** by the next
  deploy from `D:\TSC-Dashboard\precharge\`. Deliver to the drop-point, not to
  the share.
- **`requests\` exists only after the scanner has run** against
  `prechargeDeployPath`. On a fresh server the Requests tab shows
  *"Could not load requests/index.json"* until the first scan; after that it
  is `requests: []` at worst. Your existing empty-state text is right.

## 3. Delivery flow after the move (what changes for you: only the path)

1. You ship a revision (`calculator.html`, `set-password.html`).
2. Dan copies them into **`D:\TSC-Dashboard\precharge\`** on the server (over
   the admin share, or however IT grants him write there — the migration
   handoff asks for write on `D:\TSC-Dashboard\scripts`; the same grant must
   cover `D:\TSC-Dashboard\precharge`).
3. Dan runs, on the server or from his PC against the server folder:
   ```
   powershell -ExecutionPolicy Bypass -File D:\TSC-Dashboard\scripts\Deploy-Dashboard.ps1
   ```
   It prints `Published precharge\calculator.html to <prechargeDeployPath>` and
   the same for `set-password.html`, `gate-config.js`, `gate-fragment.html`.
4. Nothing else. The scanner keeps writing `requests\` on its schedule; the
   password file is untouched by a redeploy unless Dan regenerates it.

Until the server task is live the sequence is identical on Dan's PC with
`C:\` instead of `D:\`, which is what has been running this week.

## 4. `config.json` lines that concern the calculator

```json
"deployPath":          "<local folder behind \\sacred\\dashboard>",
"prechargeDeployPath": "<local folder behind \\sacred>\\precharge",
```

On the server these become local paths (the share lives on the same box);
UNC still works. `prechargeDeployPath` must be the folder IIS serves as
`/sacred/precharge/` — if it is not, the page and the `requests\` folder end
up in different places and the Requests tab is empty. The scanner creates
`requests\` and `requests\archive\` itself; nobody pre-creates them.

## 5. What your page must keep true on the server

- **Plain `http://`, not `https://`.** No `crypto.subtle`, no secure-context
  APIs, no service worker. (Already the case — the gate hashes in pure JS for
  exactly this reason.)
- **Relative paths only.** No `file://`, no `localhost`, no absolute
  `/precharge/...` — the site root is `/sacred/`, so an absolute path would
  miss. `requests/index.json` and `gate-config.js` as siblings, as now.
- **CDN scripts.** You said the served build depends on two CDN scripts. They
  load in the *user's* browser, not on the server, so the server having no
  internet is irrelevant — but a rig's browser behind a strict proxy may block
  them. If a rig ever reports a blank calculator, that is the first suspect;
  inlining them removes the dependency and is the safer choice for a sandbox
  that rigs will reach through corporate proxies. Your call.
- **Cache.** IIS serves static files with default caching; the page already
  cache-busts `index.json`. After a redeploy of `calculator.html` users may
  need Ctrl+F5 once — worth a line in your release note rather than a code
  change.
- **Windows authentication is not on the folder yet.** Sandbox decision
  (F-25/F-25a still open). The gate remains a curtain; the request payloads
  are readable by URL to anyone on the intranet who knows the path.

## 6. The scheduled task and what it means for the inbox

The scanner runs every 10 minutes as a service account (not Dan). That is
the inbox's heartbeat: a request posted at 09:19 appears on the Requests tab
by 09:30 at the latest, with no human involved. If a request ever seems
"missing", the first check is the scan log on the server, not the page. Until
the task is registered, Dan runs the scanner by hand and the tab only updates
when he does; this week's "request not showing" reports were all that.
